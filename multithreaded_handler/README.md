# Анализ URL на Go — Worker Pool, Fan-out и Fan-in

Учебное практическое задание по конкурентности в Go. Программа обрабатывает
список URL с помощью **ограниченного числа воркеров** и выводит сводный отчёт.

> **Важно:** HTTP-запросы не выполняются. Функция `simulateRequest` имитирует
> запрос с помощью `time.Sleep` и случайной задержки от 100 до 400 мс.

## Состав проекта

- `main.go` — программа: структуры `Job`, `Result`, воркеры, конвейер и отчёт.
- `main_test.go` — тесты количества и уникальности результатов, статусов, времени и статистики.
- `go.mod` — модуль Go (совместим с Go 1.16+).
- `.gitignore` — исключения для Git.

## Как запустить

Установите [Go](https://go.dev/dl/) версии 1.16 или новее и откройте терминал
в папке с `go.mod`.

```bash
go run .
```

По умолчанию запускается **5 воркеров**. Можно изменить лимит:

```bash
go run . -workers=3
```

Собрать исполняемый файл:

```bash
go build -o url-worker-pool .
```

На Windows исполняемый файл можно собрать командой:

```powershell
go build -o url-worker-pool.exe .
.\url-worker-pool.exe -workers=5
```

Изменить список URL можно в `main.go` в переменной `urls`.

## Архитектура

```text
                      Fan-out
список URL -> jobs -> worker 1 --\
                      worker 2 ---\
                      worker 3 ----> results -> main -> отчёт
                      worker 4 ---/       Fan-in
                      worker 5 --/

producer: отправляет все jobs и закрывает jobs
workers:  читают jobs, имитируют запрос, отправляют Result
closer:   ждёт wg.Wait() и закрывает results
main:     читает results до закрытия, сортирует и выводит статистику
```

- `jobs` и `results` — небуферизованные каналы: это простой вариант с
  естественным ограничением потока данных. Буферизация для корректности не нужна.
- **Fan-out** — ровно `N` воркеров конкурентно читают задания из канала `jobs`.
- **Worker Pool** — одновременно выполняется не больше `N` имитаций запросов.
- **Fan-in** — все воркеры записывают результаты в общий `results`, который
  читает главная горутина.
- `sync.WaitGroup` позволяет дождаться всех воркеров перед `close(results)`.
- Канал `jobs` закрывает единственный отправитель, а `results` — отдельная
  горутина после завершения воркеров. Благодаря этому нет отправки в закрытый канал.
- Отправка заданий вынесена в горутину, поэтому главная горутина одновременно
  принимает результаты и не возникает deadlock на небуферизованных каналах.
- Результаты приходят не по порядку; перед выводом сортируются по `Job.ID`.
- Слайс результатов заполняет только главная горутина. Гонки данных исключены.

**Время запроса** — сколько заняла отдельная имитация; **общее время программы**
— время прохождения всего конвейера. При параллельной работе второе, как правило,
меньше суммы времен всех запросов.

## Проверка

Запустить тесты:

```bash
go test ./...
```

Проверить отсутствие гонок данных (требуется поддержка race detector):

```bash
go test -race ./...
```

Тесты проверяют, что каждый URL обработан ровно один раз и не потерян, включая
случаи с одним воркером и пустым списком, а статистика считается верно.
